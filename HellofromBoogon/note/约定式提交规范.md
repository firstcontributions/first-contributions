# 约定式提交规范指南

本文依据 Conventional Commits 1.0.0（[中文版](https://www.conventionalcommits.org/zh-hans/v1.0.0/)）编写。文中"应"表示强制性要求，"宜"表示推荐做法，"可"表示允许的行为。

## 1 引言

约定式提交（Conventional Commits）是面向提交说明的轻量级书写约定。采用该约定后，提交历史具有统一结构，可用于：

a) 自动生成变更日志（CHANGELOG）；

b) 依据改动性质判定语义化版本（SemVer）的升级幅度；

c) 提升提交历史的可读性与可检索性。

## 2 提交信息结构

提交信息由头部（header）、正文（body）与脚注（footer）组成，正文与脚注为可选部分：

```text
<类型>[可选 作用域]: <描述>

[可选 正文]

[可选 脚注]
```

头部应满足下列约束：

a) 头部整体不超过 100 字符；

b) 类型与描述之间以冒号加一个空格分隔；

c) 描述宜使用祈使语气：英文语境使用动词原形（如 add，而非 added 或 adds），结尾不加句号；中文语境直接书写；

d) 正文与头部之间以一个空行分隔，内容应说明改动的动机或背景，不应复述代码本身可表达的信息。

## 3 类型

类型说明本次改动的性质。规范将 feat 与 fix 规定为基本类型，其余类型源自 Angular 约定，属社区通用扩展。

| 类型 | 含义 | 对版本号的影响 |
| --- | --- | --- |
| feat | 新增功能 | 次版本号 |
| fix | 修复缺陷 | 修订号 |
| docs | 仅涉及文档 | 无 |
| style | 仅涉及代码格式（空白、分号等），不影响程序含义 | 无 |
| refactor | 既非新增功能亦非修复缺陷的代码变更 | 无 |
| perf | 提升性能 | 无 |
| test | 新增或修正测试 | 无 |
| build | 构建系统或外部依赖的变更 | 无 |
| ci | 持续集成配置与脚本的变更 | 无 |
| chore | 不涉及源码与测试的其他变更 | 无 |
| revert | 回滚既有提交 | 随被回滚提交而定 |

## 4 破坏性变更

破坏性变更应以下列方式之一标识：

a) 在类型或作用域之后附加感叹号（!）；

b) 在正文或脚注中包含 BREAKING CHANGE 说明。

示例：

```text
feat!: 调整配置文件的默认路径

BREAKING CHANGE: 环境变量 CONFIG_PATH 不再支持相对路径，需改为绝对路径。
```

含破坏性变更的提交应同时说明变更内容与迁移方式。

## 5 作用域

作用域标注改动影响的模块或范围，置于类型之后的圆括号内：

```text
feat(parser): 支持嵌套代码块
fix(ui): 修正暗色主题下的按钮对比度
```

## 6 脚注

脚注采用 `token: value` 或 `token #编号` 的格式，用于关联议题、记录审阅者、说明破坏性变更等：

```text
fix: 修正空指针崩溃

Closes #42
Reviewed-by: Z
```

## 7 回滚提交

回滚提交以 revert 为类型前缀，头部为被回滚提交的头部，正文应引用被回滚提交的完整 SHA：

```text
revert: feat(parser): 支持嵌套代码块

This reverts commit 667ecc1654a317a13331b23ea82c02d3f5c03a1c.
```

## 8 与语义化版本的关系

| 提交内容 | 版本号动作 |
| --- | --- |
| fix | 升修订号（1.0.0 → 1.0.1） |
| feat | 升次版本号（1.0.0 → 1.1.0） |
| 破坏性变更 | 升主版本号（1.0.0 → 2.0.0） |
| 其余类型 | 不影响版本号 |

## 9 示例

### 9.1 符合规范的提交

```text
feat(auth): 支持手机号验证码登录
fix: 修正窗口在多显示器下的错位问题
docs: 增加贡献指南
refactor!: 移除已废弃的 v1 配置格式
```

### 9.2 不符合规范的提交

| 示例 | 缺陷 |
| --- | --- |
| 修改了一些东西 | 无类型，描述无信息量 |
| update | 无类型，描述无信息量 |
| fix bug | 未说明修复对象 |
| added new feature | 无类型；时态误用过去时 |
| docs:增加链接 | 类型正确，冒号后缺少空格 |

## 10 编写建议

a) 一个提交应只包含一类性质的改动；无法确定单一类型时，宜将其拆分为多个提交；

b) 提交前宜通过 git diff --staged 核对暂存内容，再确定类型；

c) 区分 feat 与 fix 的依据：改动使软件能够执行新的功能，属于 feat；将本应正确的行为修正，属于 fix；

d) 描述不应使用"修改了一些内容"等无信息量表述。
